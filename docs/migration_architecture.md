# Architecture Design & Migration Document

## 1. Executive Summary
Аналіз декомпільованої бази коду (`game.swf`) підтвердив, що гра має монолітну ActionScript 3 архітектуру (Offline-first). Серверна частина (бекенд) повністю відсутня — немає жодних мережевих запитів (`URLLoader`, `Socket`, `NetConnection`). Уся логіка, баланс і збереження прогресу відбуваються на стороні клієнта за допомогою `SharedObject`. 

Інтеграція з соціальною мережею (ВКонтакті) визнана **технічним боргом (Technical Debt)**, який більше не підтримується і має бути повністю видалений або замінений на заглушки під час міграції.

Пряма автоматична конвертація коду неможлива через гігантські розміри "God-класів" (до 23 тисяч рядків) і жорстку прив'язку бізнес-логіки до візуальних кадрів анімації (`gotoAndStop`). Однак, фізика та колізії базуються на чистій математиці (без `hitTest`), що суттєво спрощує її перенесення на сучасні HTML5 Canvas/WebGL рушії (напр., Phaser 3).

## 2. Карта архітектури гри

### Точка входу (Top-level Entry Flow)
- **`FWP.as` (конструктор, рядок 586)**: Спрацьовує при запуску. 
- **Ініціалізація**: Створюються масиви конфігурацій, об'єкти профілю гравця (`player`).
- **Завантаження ресурсів**: `Loader.loadBytes()` розпаковує вбудовані `BinaryData` карти, звуки та UI (напр., рядки 725-727).
- **Зовнішні API (VK)**: Ініціалізується `this.VK = new EIApiConnection()`. (Підлягає видаленню).

### Ключові модулі та "God-класи"
Вся гра зосереджена в 5 велетенських класах (у папці `classes/`):
1. **`FWP.as` (816 КБ, ~23,600 рядків)**: Головний контролер. Зберігає всі дані гравця, конфігурації, керує `SharedObject`.
2. **`world.as` (774 КБ)**: Відповідає за рендеринг мапи. Керує шарами світу, прокруткою камери, фізичними розрахунками перешкод (через математичні формули, а не hitTest).
3. **`new_interf.as` (547 КБ)**: Модуль UI. Керує всіма меню через масові виклики `gotoAndStop` (більше 160 викликів).
4. **`obj.as` (175 КБ)**: Система сутностей (гравці, боси, хробаки, зброя). Бойова логіка жорстко переплетена з анімацією (`gotoAndStop`).
5. **`proc.as` (123 КБ)**: Допоміжні ігрові процедури та розрахунки.

## 3. Інвентаризація даних і ресурсів
Гра не використовує зовнішніх конфігів (ні XML, ні JSON). Усе захардкоджено.
- **Типи Assets**: Зображення (1642), Звуки (42), Спрайти (6436). 
- **Зберігання**: Вони запаковані як вкладені SWF-файли всередині `game.swf` і вже видобуті у вигляді окремих ресурсів.
- **Тексти та налаштування**: Знаходяться безпосередньо в коді `FWP.as` (наприклад, масив `ADVICES`, конфігурація `auc_weapons`).
- **Локальні збереження**: `SharedObject.getLocal("local_data")` (`FWP.as`, рядок 692).

## 4. Аналіз зовнішніх залежностей та VK Integration (Legacy)
- **Бекенд/Мережа**: **Відсутні**. (0 викликів `URLLoader` чи `NetConnection`).
- **VK API (`vk/EIApiConnection.as`)**: Використовував `ExternalInterface.call` для комунікації з JavaScript. **Стратегія міграції: Safe Removal**. Весь соціальний функціонал (запити друзів, рейтинги) підлягає видаленню. Функції монетизації (отримання валюти) можна ізолювати у вигляді чит-кодів або внутрішньоігрової нагороди.
- **Зовнішні посилання**: Виклики `navigateToURL` (переходи на сторінки груп ВКонтакті). **Стратегія: Safe Removal**.

## 5. Оцінка перенесення та ризики
### Migration Risks (Ризики)
1. **Зчеплення візуалу і логіки (Coupling)**: Стан об'єктів повністю залежить від поточного кадру анімації (`gotoAndStop`). Логіку доведеться переписувати на систему кінцевих автоматів (State Machines). Проте гарною новиною є те, що гра не покладається на `currentFrame`, що означає, що логіка сама жорстко диктує стан візуалу, а не навпаки.
2. **Математична колізія**: Колізії реалізовані через чисту математику (відсутні виклики `hitTestPoint` чи `hitTestObject`). Це величезний плюс, адже формули (напр. `Math.sqrt`) можна легко скопіювати на TypeScript один до одного.
3. **Карти рівнів**: Рівні є окремими SWF-файлами. Оскільки колізії там математичні, скоріш за все карти будувалися з блоків за чіткою сіткою. Потрібно створити конвертер рівнів (Level Parser) для перетворення розібраних ресурсів карт у Tilemap JSON.

### Рекомендований сучасний стек
- **Клієнт (Геймплей)**: **Phaser 3**. Phaser чудово підходить для ігор з фізикою, спрайтами та математичними колізіями.
- **Мова програмування**: **TypeScript**. Статична типізація дуже допоможе при розплутуванні AS3 коду.
- **Клієнт (UI)**: **React** (поверх Canvas) для вікон, магазинів та меню.
- **Збереження**: HTML5 `localStorage` або IndexedDB замість `SharedObject`.

## 6. Поетапний план міграції
1. **Екстракція даних (Data Extraction)**:
   - Вручну перенести всі хардкодні масиви конфігів (ціни, перки, тексти) з `FWP.as` у `configs/game_data.json`.
2. **Створення конвертера карт (Level Parser)**:
   - Дослідити розпаковані карти (наприклад, `assets/29_FWP_ASSET_MAP_ASSAULT_1`) і написати Node.js скрипт, який перетворить їхнє наповнення на Tilemap JSON.
3. **Реалізація рушія сутностей (Core Loop & Entities)**:
   - Переписати `obj.as` на чисту логіку (без рендерингу). Виділити класи `Worm`, `Weapon`, `Projectile`.
4. **Видалення Technical Debt (VK API)**:
   - Ігнорувати весь код з `EIApiConnection.as` та `ExternalInterface`.
5. **Система рендерингу та UI**:
   - Прив'язати сучасні спрайт-анімації та реалізувати UI на React.
